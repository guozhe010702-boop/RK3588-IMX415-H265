# Windows 控制台优化：调研、实现与下一步

调研日期：2026-10-13。针对已交付的 1.0.0，现实现 1.1.0。优先处理预览开销、连接切换、下载完整性和退出响应；板端继续使用既有 FFmpeg、RK3588 VPU 和 MediaMTX 链路。

## 1. 为什么先优化这些地方

现有链路已经通过实际 H.265/H.264、HDMI、MP4 和 30 分钟运行验证。代码检查发现：关闭窗口会在界面线程等待后台线程；日志每新增一条就重建整个文本框；同名下载只凭长度判断已完成；播放进程创建与切换之间存在竞态。这些问题可以通过明确的回归测试验证，先处理它们能直接改善当前软件。

| 调研对象 | 可采用的经验 | 本项目的选择 |
| --- | --- | --- |
| [Qt QProcess 官方文档](https://doc.qt.io/qtforpython-6/PySide6/QtCore/QProcess.html) | 在界面线程阻塞等待进程可能造成界面冻结 | 继续让独立 FFmpeg 在后台运行，关闭时由定时器检查退出状态；不在界面线程调用线程 wait |
| [Qt QPlainTextEdit 官方文档](https://doc.qt.io/qtforpython-6/PySide6/QtWidgets/QPlainTextEdit.html) | 限制段落数量并追加文本适合日志查看 | 日志每 200 ms 批量追加，最多显示 1000 段，保留用户阅读位置 |
| [BelEye 架构文档](https://github.com/belkaniacode/BelEye/blob/main/docs/ARCHITECTURE.md) | 作者记录了多个预览中 BGR 图像拷贝和重绘的瓶颈 | 增加预览尺寸与帧率档位，继续只保留最新帧；其多画面测量不能直接等同于本项目单画面性能 |
| [FFmpeg fps 滤镜](https://ffmpeg.org/ffmpeg-filters.html#fps) | 可按输出帧率丢帧或补帧 | 在电脑端限帧、缩放，减少管道数据与绘制工作；板端编码参数不受影响 |
| [Paramiko SFTP 官方文档](https://docs.paramiko.org/en/stable/api/sftp.html) | 预取请求需要设置并发上限和通道超时 | 保留 16 个预取请求、独立文件连接，并增加内容校验和进度节流 |
| [MediaMTX 指标文档](https://mediamtx.org/docs/features/metrics) | 提供 Prometheus 格式的路径、字节和客户端指标 | 下一阶段作为网络速率与故障诊断数据源，当前版本未启用新的指标服务 |

这些来源用于判断实现方向；性能收益以本机实测为准。

## 2. 本次已经实现的优化

### 电脑预览三档

| 档位 | 最大宽度 | 预览输出帧率 | 1080p 来源对应尺寸 | 理论 BGR 数据量 |
| --- | --- | --- | --- | --- |
| 流畅 | 640 | 15 fps | 640×360 | 10.37 MB/s |
| 均衡 | 960 | 30 fps | 960×540 | 46.66 MB/s |
| 清晰 | 1280 | 30 fps | 1280×720 | 82.94 MB/s |

数据量按宽×高×3 字节×帧率计算，单位 MB/s 为十进制。流畅相对清晰减少 87.5% 的原始像素传输量，**不代表 CPU 同比例下降**，因为电脑仍要解码输入的 1080p H.265。默认保持清晰；选择会保存到个人配置。

首页显示预览尺寸、解码帧率、显示帧率、自动重连次数和首帧等待时间。首帧时间指电脑 FFmpeg 进程创建后到第一张完整输出帧；它不包含全部 SSH 握手时间，也不是摄像头到屏幕的端到端延迟。编码帧率卡片继续显示板端编码进度。

### 连接与进程生命周期

SSH 与文件任务携带会话编号；更换连接或手动断开后，尚未执行的旧任务不再用于新连接。正在执行的远程启停或录像操作不会自动重发；断开控制连接不能推断远端操作已经取消。

每次重建预览增加代次编号。FFmpeg 创建后再次核对代次，旧进程不发布新画面；监测器使用该进程自己的出帧时间，避免旧监测线程终止新播放器。创建失败、暂停和异常退出均走统一清理。关闭窗口通过异步检查等待资源退出，板端直播、HDMI 和录像继续运行。

### 文件校验与界面刷新

下载前在独立 SSH 文件连接中执行固定 Python 校验程序，文件路径通过 JSON 标准输入传递。仅允许录像/截图目录内的普通、已完成文件。校验程序核对读取前后的长度与修改时间，然后给出 SHA-256。

下载过程计算 SHA-256，写入临时文件、刷新磁盘，再读取本地文件复核；长度与摘要均正确后才更名为最终文件。同名且同长度的本地文件也必须摘要相同才能复用，内容不同则保留原文件并提示更换目录。下载取消或校验失败会清理临时文件。进度最多每 100 ms 更新一次，完成时立即更新。

大录像的摘要计算需要额外读取板端磁盘，不能当作零开销。当前校验命令等待上限为 30 秒，特别大的文件或慢存储可能超时并提示重试；分段校验和断点续传留到后续版本。

日志每 200 ms 合并写入和追加显示；切换分类才重建显示。窗口保留最近 1000 条事件，已有 2 MiB 日志轮换继续工作。

## 3. 本次验收与边界

自动回归覆盖同长度但不同内容文件、错误摘要、Windows 保留文件名、显示档位持久化、宽高比、旧任务失效、解码器缺失、异步关闭与日志批量更新。实际板端测量和发布结果见 [1.1.0 优化验收记录](../history/Windows_控制台优化验收记录.md)。

这轮验收只切换电脑预览、电脑连接并下载已有录像及新截图，保持板端采集进程运行。1.0.0 的 30 分钟验收仍是历史记录，不能作为 1.1.0 新测量。Windows 10 兼容目标仍需单独机器验证。

## 4. 下一步优化顺序

| 优先级 | 下一步 | 先验证什么 | 验收标准 |
| --- | --- | --- | --- |
| P1 | 一键诊断和状态趋势 | 读取板端 CPU、内存、温度与 MediaMTX 字节计数；通过 SSH 返回 | 明确区分摄像头无帧、编码异常、网络断开、电脑解码失败；正常运行不增加明显负载 |
| P1 | 下载断点续传 | 用稳定文件摘要绑定进度；确认文件已封口与未改变 | 中断后继续；同名内容变化时拒绝续传；最终完整摘要相同 |
| P2 | Windows GPU 解码/渲染原型 | 目标电脑显卡的 H.265 支持、驱动、D3D11 和拷贝开销 | 对比现有模式 CPU、内存、首帧、端到端延迟与长时间稳定性，失败可回退 |
| P2 | 相机能力页与参数预设 | 实际 V4L2/ISP 模式、RKAIQ 自动曝光和增益控制接口 | 展示实际能力；录像期间保护参数；变更失败恢复；对照拍摄验证曝光效果 |
| P3 | 算法处理与多相机 | 帧时间戳、丢帧策略、板端资源预算 | 算法慢时不积压直播；控制、显示和处理可以独立启停 |

GPU 方案可以比较独立 FFmpeg D3D11 解码与 [mpv/libmpv](https://mpv.io/manual/master/#embedding-into-other-programs) 渲染。仅增加硬解参数仍可能把图像下载成 BGR 再复制，不能称为零拷贝。替换播放器前要测量，不直接替换已验证的默认模式。

板端方向继续参考 [ffmpeg-rockchip 编码说明](https://github.com/nyanmisaka/ffmpeg-rockchip/wiki/Encoder)。板端 MPP 硬编和电脑 GPU 硬解是两种不同设备上的操作，前者已验证，后者当前未交付。NV12M 两平面 DMA-BUF/RGA 接入也需要单独验证格式、stride、偏移和缓冲区生命周期。

曝光、增益、ROI、自动识别不会仅凭开源 UI 示例加入按钮。需要先核对本板固件接口，尤其是 RKAIQ 自动控制与手动参数如何协调。后续调研应保留“接口存在、实际生效、画面可验证”三层证据。

## 5. 使用与回退

从 [桌面操作指南](../guides/Windows_相机控制台操作指南.md) 获取新版 ZIP。解压到新目录后启动，在画面右上角选择档位。无需重新部署板端程序。

本地原 1.0.0 ZIP 保留，另有 `backups/desktop_v1.0.0/source.zip` 和 Git 标签 `before-desktop-optimization-20261013`。需要回退时关闭新版，运行旧版完整目录；关闭任一控制台均不停止板端直播。
