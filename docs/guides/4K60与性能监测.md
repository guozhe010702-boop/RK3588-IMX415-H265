# 4K60 与性能监测

本版为 Windows 控制台 1.2.2。性能面板包含真实采样、60 fps 电脑预览、CSV 和板端 VPU 硬解显示。2026-10-19 已完成 boot-only 实验内核切换，当前 IMX415 能枚举 60 fps，并已实测约 60 fps 取帧。**模式枚举、短测和完整长测分别报告，合成测试不代表真实相机。** 最新结论见 [验收记录](../history/4K60与性能监测验收.md)；驱动及回退见 [BSP 说明](../../board/bsp/imx415-4k60/README.md)。

## 使用软件

1.2.2 的性能页先显示八张实时卡片：当前电脑订阅流速、网口总 TX 占用、两端 CPU、两端内存、电脑完整解码和实际绘制。分栏中间可以拖动；小窗口中的控件自动换行，放不下的内容可滚动访问，右侧页面不会强制撑大整个窗口。

“占链路”使用当前订阅实测流速除以网口协商速率；“网口总 TX 占用”使用整个网口发送流量除以协商速率。例如一路订阅 20.2 Mbit/s、千兆链路时约 2.02%，还可能有其它客户端和协议开销，因此网口总量通常更大。CPU 卡片按所有逻辑核归一化到 0–100%；进程 CPU 仍在详细指标中，口径不同。

内存卡片为主机物理内存使用量：总量减可用量。板端使用 MemAvailable，避免把可回收文件缓存全部当作不可回收占用；电脑使用 psutil 的 available。GUI/解码进程自身 RSS 另列于详细指标。缺失显示“不可用”，断开后板端数据标记“已过期”；电脑自身资源继续更新。VPU 没有公开负载接口时仍不编造百分比。

“展开趋势图”显示历史变化；“展开详细指标与 CSV 路径”显示完整技术数据。横轴是采样时间，最初显示最近 30 秒，随采样增长至最多十分钟；刻度、图例均放在数据框外。纵轴是自动刻度，不代表硬件上限。图下明确列出已采样时长，未采样部分不会补造曲线。

“本次新增缺口”以本次连接首次有效采样为基线；“累计缺口”保留采集进程的原始计数，包括启动阶段。重连或更换进程会重新建立观测基线，不改写原计数。两者同时保存到 CSV。

解压本地 `releases/EVM3588CameraConsole-Windows-x64-v1.2.2.zip`，双击其中的 EXE。首次在“设备连接”输入 SSH 密码或选择自己的密钥；核对主机指纹。关闭软件只断开电脑端连接，不停止板端任务。

1. 已有直播会自动显示。进入“性能监测”，看每秒采样的指标和十分钟趋势。
2. “性能 60 fps”是电脑预览上限：完整码流先解码，再缩放到最大 1280 宽；不会改变直播或录像分辨率。源为 30 fps 时仍只显示约 30 fps。
3. “编码设置 → 填入 4K60 性能预设”填写 3840×2160、60 fps、H.265、20 Mbit/s、GOP 60，不会直接应用。已适配的实验系统可以请求 60 fps；原固件或未知传感器仍在停止现有直播之前拒绝不支持的高帧率。录制期间禁止重配。
4. 根据“板端能力”判断当前系统：只有枚举时显示“驱动模式已可用，完整验收尚未通过”；完整验收还需有效本地记录匹配当前 boot 哈希、运行内核、实验 DT 属性及实测阈值。普通默认仍为 1080p30、2.5 Mbit/s，4K30 可继续使用。
5. “HDMI 开启”启动板端 `hevc_rkmpp`/`h264_rkmpp` 解码，RGA 缩放至不超过 1920×1080，再交给系统 ffplay 显示。分别显示解码尺寸、送给播放器的尺寸和 xrandr 实际显示模式。硬解失败会报告错误，编码和电脑推流继续运行。

CSV 在每次软件运行时自动建立于用户数据目录的 `performance/`，UTF-8 BOM，表头固定，每秒一行。面板可选新目录、导出截至当前采样的 CSV、打开目录；换目录后另起文件。保存失败保留预览，显示错误并每 30 秒重试。没有数据的字段留空，不写成零。CSV 不含密码、密钥和连接配置，不自动上传。

## 怎样读指标

| 指标 | 口径 |
| --- | --- |
| 传感器报告帧率 | 驱动报告的标称间隔，不是实测采集速度 |
| 采集 fps | NV12M 两平面校验、有效复制完成次数的增量 / FFmpeg 内单调时钟增量；最多一秒写一条统计日志 |
| 驱动序号缺口 | 有效帧之间的 V4L2 sequence 前向缺口；包括中途被驱动或校验丢弃的编号，不能单凭它认定传感器损坏 |
| 采集错帧 | NV12M 错误标记、平面数量或边界校验失败累计数 |
| 采集缓冲数 | VIDIOC_REQBUFS 返回的实际数量，不是只显示请求值；1.2.2 请求 16 个 |
| 缓冲周转峰值 | 每个统计窗口内 DQBUF 返回到完成拷贝、QBUF 归还的最大耗时；日志在归还后写出 |
| 采集时间戳年龄峰值 | 驱动明确标记单调时钟时，从帧时间戳到 DQBUF 返回的最大间隔；包含硬件和队列路径，不是镜头到屏幕延迟 |
| 编码 fps | `-progress` 输出帧数的相邻增量 / 接收块的单调时间间隔；与累计平均 `fps` 旧字段分开 |
| 板端硬解 fps | 独立硬解进程输出计数差分；无 fps 滤镜和补帧，统计在 RGA 缩放之后，受整条输出路径的反压影响 |
| 电脑解码 fps | `showinfo@decoded` 放在 fps/缩放滤镜之前，关闭校验和，统计完整源尺寸的解码输出 |
| Qt 绘制 fps | `paintEvent` 真正绘制的新帧次数；控件重绘同一张图只算一次，不等于显示器刷新率或镜头到屏幕延迟 |
| 预览丢弃 | 原始帧拼接时丢弃旧完整帧、最新帧邮箱被替换，以及 Qt 绘制前被替换的画面；不包含有意的预览 fps 降采样 |
| 目标码率 | 配置的编码目标；不是实测流量 |
| RTSP Mbit/s | MediaMTX 路径 inboundBytes 增量；使用十进制 1 Mbit = 1,000,000 bit |
| 本订阅 Mbit/s | 当前 VideoWorker 的随机 `console` 标识对应的 RTSP 会话 outboundBytes 差分；排除 HDMI、录像和别的播放器 |
| 网口 TX / RX | 活跃有线接口中 TX 最高者，展示接口名；是整块网口的总量，包括其它业务和协议开销 |
| 链路占用 | 分别用 TX、RX 速率 / 协商速率，不把全双工两个方向相加 |
| 主机 CPU | 全部逻辑核归一化至 0–100%；进程 CPU 以一个逻辑核 100%，多线程进程可以超过 100% |
| 内存 | 进程 RSS，单位 MiB；不是总分配量或显存占用 |
| VPU 频率 | 只读取内核公开的 devfreq 节点；无节点显示不可用，不用进程 CPU 冒充 VPU 利用率 |

首次差分、进程重启、计数回退或 RTSP 会话变化时重新建立基线。板端采样超过 3 秒未更新会标记过期；视频超过 4 秒无新帧时停止展示旧帧率。恢复后的历史日志仍可查看，但不当作当前故障。低于 55 fps 的提醒仅针对源和预览上限都接近 60 fps 的场景，不把正常 30 fps 源误报成 60 fps 瓶颈。

窗口被最小化或完全遮挡时，Qt 可能不绘制，Windows 也可能限制后台进程；这时绘制为 0 是真实记录，不能解释成相机 0 fps。1.2.1 的 CSV 增加 window_minimized；最小化时明确显示该状态，保留实际绘制值，不把它误报为相机性能故障。做前台绘制验收时应保持测试窗口可见；后台解码、板端采集和实际绘制分别看。测试中不将最小化试验改写为已通过的前台测试。

1.2.1 的性能预览用 4 个软件解码线程，允许 frame+slice；普通预览保留原 low_delay 设置。[FFmpeg 线程实现](https://github.com/FFmpeg/FFmpeg/blob/master/libavcodec/pthread.c)明确在 low_delay 下禁用帧级并行。本机同一段真实录像、同一缩放/RGB 输出的吞吐对比约为 45 → 195 fps，不能当成相机输出帧率；单独修改缩放算法没有明显收益，因此保留原 bicubic。帧线程带来少量解码缓冲，本轮没有测量精确镜头到屏幕延迟。

能力记录位于板端 `state/camera-validation.json`，普通部署不会生成“通过”标志。只有真实相机、局域网、至少 1800 秒、有效计数窗口至少 1790 秒，采集/编码/两端解码均 ≥59 fps、Qt 绘制 ≥55 fps，且新增序号缺口/错帧/补帧/编码丢帧/预热后解码错误均为 0，才可通过。记录过期于不同 boot、内核或缺少实验属性时不会继续显示通过。

## 更新与命令解释

### 采集缺口的定位工具

第三个采集补丁保留原始 sequence 缺口计数，并在 `AV_CAPTURE_GAP` 中记录前后序号、缺失数量、时间戳年龄和缓冲归还耗时。16 个 mmap 缓冲及连续平面批量复制用于减轻应用侧压力；它们并不等于已经解决 CIF→ISP 的上游 RAW 回读缺口。中断分配只是独立试验，未证明有效之前不作为默认启动策略。

下面这条在 **Windows PowerShell，av_dev 根目录**执行：

```powershell
.\.venv-desktop\Scripts\python.exe .\tools\tests\inspect_capture_runtime.py --output .\.cache\capture-diagnostics.json
```

解释：使用项目独立 Python，通过本机现有 ADB 只读采集进程参数、帧统计、CIF/ISP 信息、中断分配和内核日志；`--output` 指定本地 JSON 文件。不会重启、改参数或刷写。此工具按本项目已知 ADB 路径定位，输出仅在本地保存。

以下三条在 **开发板 Bash** 执行，独立于桌面按钮。应先查看当前直播状态，避免把调度条件变化混进同一段验收。

```bash
python3 /userdata/av_dev/ffmpeg_pipeline/tune_capture_irqs.py
```

解释：默认只读，列出本机活跃 CIF/ISP 中断、当前亲和性与候选大核；不写入任何设置。仅支持 RK3588，缺少合适 CPU、共享中断或 irqbalance 在运行时拒绝试验。

```bash
python3 /userdata/av_dev/ffmpeg_pipeline/tune_capture_irqs.py --apply
```

解释：`--apply` 先备份本次启动的原亲和性，再将 CIF 和 ISP 分配到不同大核并读回验证；不修改网口/VPU 中断、时钟或调度优先级，不写 boot。运行时更改不会跨重启保留。

```bash
python3 /userdata/av_dev/ffmpeg_pipeline/tune_capture_irqs.py --restore
```

解释：`--restore` 根据本次启动的备份恢复原设置；若已重启、设置被外部程序改动或备份不匹配，会拒绝覆盖。它不是固件回退工具。正式默认链路不自动执行上述调度试验。

### AIQ RAW 线程调度

这是与 IRQ 亲和性分开的、显式启用的软件调度优化。只匹配实际持有 RAW `/dev/video0` 的 `/usr/bin/rkaiq_3A_server`，将 `isp_tx_poll`、`isp_rx_poll`、`RawProcThread` 三个阻塞式交接线程设为 `SCHED_RR`、优先级 5。算法线程、编码器和 IRQ 保持原设置；没有修改内核、厂商库或传感器时序。

RR 可以让就绪的交接线程优先于普通线程运行，并在同优先级内轮转；它不是每秒额外生成帧的机制，也不能保证消除全部硬件或内存瓶颈。[Linux 调度说明](https://man7.org/linux/man-pages/man7/sched.7.html)。已有自定义调度、线程不完整或身份不匹配时，程序保留原设置并报告原因。

以下三条命令在 **开发板 Bash** 执行，需要已经部署新版板端模块。配置只写入本机 `state/raw-scheduler-enabled.json`；普通源码部署不自动启用。控制服务运行时按秒应用/恢复；若服务未运行，启用文件只在下次服务启动后生效。

```bash
python3 /userdata/av_dev/ffmpeg_pipeline/tune_raw_scheduler.py
```

解释：不加参数只读取启用标志和调度备份，不修改线程。实时应用结果查看已有 `avctl.py status` 的 `captureScheduling` 字段，`active` 为实际生效状态，`error` 为失败原因。

```bash
python3 /userdata/av_dev/ffmpeg_pipeline/tune_raw_scheduler.py --enable
```

解释：`--enable` 显式允许控制服务对本板 4K、≥50 fps 直播应用上述调度；只在确认三个线程身份后执行，先保存原策略、TID、启动时间和 boot ID，再写入并读回。启用标志保留在本机，但不启用直播开机自启动。

```bash
python3 /userdata/av_dev/ffmpeg_pipeline/tune_raw_scheduler.py --disable
```

解释：`--disable` 关闭允许标志；运行中的控制服务下一次巡检会恢复原策略，不停止直播。停止直播或切回 1080p30 也会恢复；线程编号被复用、设置被外部程序改过时不覆盖新任务或外部设置。

以下命令在 **开发板 Bash** 执行；先让直播完成暖机，不要与主动启停或参数切换测试混在同一窗口。

```bash
python3 /userdata/av_dev/ffmpeg_pipeline/tests/capture_stability.py --seconds 1800 --output /userdata/av_dev/ffmpeg_pipeline/state/continuity-run-01
```

解释：只观察当前直播，不打开相机、不改参数。`--seconds 1800` 要求至少 30 分钟有效观察，`--output` 是新建结果目录，已存在时拒绝覆盖。保存逐秒原始 JSONL、初末计数和失败原因；新增缺口、计数重置、进程更换、过期统计、编码补帧/丢帧或时长不足均不能判定通过。启动前已有的累计缺口仍保留，只将本窗口增量作为连续性结果。该工具验证板端采集，不能替代电脑 Qt 绘制和完整链路验收。

以下两条在 **Windows PowerShell，av_dev 根目录**执行。

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\deploy\deploy.ps1
```

解释：上传当前板端程序与补丁，不包含 BSP、内核和私人配置，不自动重启。`-NoProfile` 不加载个人 PowerShell 配置，`-ExecutionPolicy Bypass` 只影响此进程，`-File` 指定部署脚本。

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\desktop\run.ps1
```

解释：用已有独立环境启动源码版 Qt 软件；脚本参数含义同上一条，路径改为桌面启动脚本。便携包用户直接双击 EXE。

以下命令在 **开发板 Bash** 执行。重建前应结束录像并按需停止直播，升级控制服务会中断其子进程。

```bash
bash /userdata/av_dev/ffmpeg_pipeline/build_capture_metrics.sh
```

解释：只对已构建的私有 FFmpeg 增量应用第二、第三个补丁、用 4 个编译任务重建并原子替换两个私有可执行文件。保留系统 FFmpeg、厂商库和 3A 服务；修正厂商头文件搜索环境造成的重复构建问题。首次构建仍使用原 `build_runtime.sh`。

```bash
systemctl restart evm-ffmpeg-control.service
```

解释：让 systemd 重启控制服务以加载新 Python 模块，原直播和 HDMI 会停止；**不要在录像时执行**。这个命令不会升级内核或启用开机自启动。

```bash
python3 /userdata/av_dev/ffmpeg_pipeline/avctl.py start
```

解释：使用保存的配置启动一次采集硬编；必要时启动服务，不会创建两个摄像头采集器。

```bash
python3 /userdata/av_dev/ffmpeg_pipeline/avctl.py decode-start
```

解释：读取已有 RTSP，启动 VPU 硬解、RGA 和 HDMI 显示，不再次打开摄像头。`decode-stop` 仅结束这条解码显示支路。

```bash
python3 /userdata/av_dev/ffmpeg_pipeline/avctl.py status
```

解释：读取当前直播、录像、解码及性能缓存，结果为 JSON。服务停止但 socket 遗留时会返回“服务未运行”，SSH 本身仍可正常连接。

```bash
python3 /userdata/av_dev/ffmpeg_pipeline/tests/codec_4k60.py --frames 600 --output /userdata/av_dev/ffmpeg_pipeline/state/acceptance-4k60
```

解释：生成 600 帧合成 4K60 图像，硬编 MP4 后硬解并 RGA 缩放，保存计数、日志和 MPP 设备观察结果到 `--output` 目录。它不采集摄像头，输出结果不能替代真实 4K60。该测试会占用 VPU，不要与正式性能验收混在同一个统计窗口内。

内核实验的步骤、备份与回退边界见 [BSP 说明](../../board/bsp/imx415-4k60/README.md)。未做系统切换前，不能在软件里真正打开 4K60。

- [ffmpeg-rockchip Decoder](https://github.com/nyanmisaka/ffmpeg-rockchip/wiki/Decoder)：显式 RKMPP 硬解和 DRM PRIME。
- [MediaMTX v1.21.2 API](https://github.com/bluenviron/mediamtx/blob/v1.21.2/api/openapi.yaml)：使用会话 query、id、inboundBytes、outboundBytes，不累计所有订阅者冒充本机带宽。
