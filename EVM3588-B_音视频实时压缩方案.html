01 / 需求拆解

你要做的事，拆成四个数据处理环节

“拿到摄像头源数据，做音视频处理，再实时压缩图像帧”本质是一条媒体数据流水线。每个环节 RK3588 都有对应的硬件单元，不需要 CPU 软编。

① 采集

获取源数据

IMX415 经 MIPI CSI-2 送入 RKISP，3A（AE/AWB/AF）成像后以 NV12 原始帧输出到 V4L2 节点 /dev/video44。这就是“源数据”。

② 预处理

在数据源处理

用 RGA 硬件 2D 引擎做缩放、裁剪、旋转、色彩空间转换、格式对齐（stride），不占 CPU。例如 4K 缩到 1080p、NV12 直通。

③ 实时压缩

硬件编码帧

NV12 帧送入 MPP/VENC，逐帧做 H.264/H.265 帧内+帧间压缩，输出带时间戳的压缩码流。这是“经典视频压缩算法”的硬件落地。

④ 输出

封装 / 推流

裸码流封装为 MP4/TS 落盘，或经 RTP/UDP/RTSP 实时推到电脑；音频 AAC 编码后与视频同步复用（mux）。

关键认知：“经典压缩算法”（H.264/H.265 的预测、变换、量化、熵编码）在 RK3588 上由 VENC 硬件电路完成，软件通过 MPP 接口喂帧、取码流即可。你既可以用 GStreamer 一行管线快速跑通，也可以用 MPP 的 C API 自己掌控每一帧——本方案两条路都给。

05 / 压缩算法

为什么必须压缩，H.264/H.265 在做什么

先看原始数据量，再理解硬件编码器每一帧做了哪些“经典压缩”动作。

原始码率 vs 压缩码率（NV12，30fps，实算）

1080p30 原始 NV12
746.5 Mbps · 89.0 MB/s
1080p30 H.264
4 Mbps
4K30 原始 NV12
2986 Mbps (≈2.99 Gbps) · 356 MB/s
4K30 H.265
12 Mbps

单帧原始大小：1080p NV12 ≈ 2.97 MB，4K NV12 ≈ 11.87 MB。压缩比约 187:1（1080p） 与 249:1（4K）。不压缩，网口和 eMMC 都无法实时承载——这就是必须硬件编码的原因。

三种编码格式怎么选

格式特点适用
H.264
MPP type 7		兼容性较好，旧示例支持兼容性参考；当前主链路不使用
H.265/HEVC
type 16777220		同等画质省码率 30~45%，编解码更重4K、带宽/存储受限
MJPEG
type 8		每帧独立 JPEG，无帧间压缩，码率大抓拍、低延迟逐帧、简单分析

当前主链路选择 H.265，由 hevc_rkmpp 硬编，通过 RTSP TCP 分发。H.264 已提供配置入口，完整实测仍以 H.265 为准；旧 GStreamer 示例保留。

硬件编码器每帧做的事

  • 帧内预测（I 帧）：在帧内按块预测，去除空间冗余，可独立解码
  • 帧间预测（P/B 帧）：运动估计+运动补偿，参考相邻帧，只编码“差异”，去除时间冗余（压缩主力）
  • 变换+量化：DCT 变换到频域后量化，丢弃人眼不敏感的高频
  • 环路滤波 / SAO：抑制块效应（H.265 更强）
  • 熵编码：H.264 CABAC / H.265 CABAC，无损压缩语法元素

这些步骤由 VENC 电路在帧级别并行完成，你通过 MPP 配置 Profile/Level/GOP/码率，再喂 NV12 帧即可。

GOP 图像组结构（决定延迟与压缩率）

码率控制（RC）：CBR / VBR / FIXQP

模式行为本方案用途
CBR恒定码率，围绕 bps_target 波动，带宽可预测实时推流首选，脚本默认 rc-mode=cbr

MPP 配置字段：rc:mode、rc:bps_target/max/min、rc:gop、h264:profile/level，在 C 程序与 GStreamer 的 bps/gop/rc-mode 属性中一一对应。

mpp_frame_set_fmt(frm, MPP_FMT_YUV420SP);
mpp_frame_set_pts(frm, frame_index*1000000/fps);
mpi->encode_put_frame(ctx, frm);                      // 提交编码；按缓冲生命周期管理复用
mpp_frame_deinit(&frm);

mpi->encode_get_packet(ctx, &pkt);                    // 取 H.265 包；分片时循环至 EOI
fwrite(mpp_packet_get_pos(pkt), 1, mpp_packet_get_length(pkt), fp);
mpp_packet_deinit(&pkt);

从 /dev/video44 取 NV12 帧（V4L2 MMAP）

本板 /dev/video44 是多平面采集节点，实际格式为 NV12M（fourcc NM12）。Y/UV 各有独立的 MMAP 缓冲与 bytesperline；逐行复制到 MPP 对齐缓冲后再编码，不能把两平面当作一块连续内存。下方是调用顺序示意，完整可编译代码在 v4l2_mpp_enc.c。

V4L2 采集关键步骤
fmt.type = V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE;
fmt.fmt.pix_mp.width = w; fmt.fmt.pix_mp.height = h;
fmt.fmt.pix_mp.pixelformat = V4L2_PIX_FMT_NV12M;
ioctl(fd, VIDIOC_S_FMT, &fmt);
y_pitch  = fmt.fmt.pix_mp.plane_fmt[0].bytesperline;
uv_pitch = fmt.fmt.pix_mp.plane_fmt[1].bytesperline;

req.type = V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE;
req.count = 4; req.memory = V4L2_MEMORY_MMAP;
ioctl(fd, VIDIOC_REQBUFS, &req);
for (i=0;i<req.count;i++){
    b.length = 2; b.m.planes = planes;
    ioctl(fd, VIDIOC_QUERYBUF, &b);
    mmap_y_and_uv_separately(planes[0], planes[1]);
    ioctl(fd, VIDIOC_QBUF, &b);
}
ioctl(fd, VIDIOC_STREAMON, &type);
// 主循环：DQBUF 取两平面 -> 逐行复制/送 MPP -> QBUF 归还
b.length = 2; b.m.planes = planes;
ioctl(fd, VIDIOC_DQBUF, &b);
h265_encoder_frame(... y, y_pitch, uv, uv_pitch ...);
ioctl(fd, VIDIOC_QBUF, &b);
零拷贝升级方向：将 V4L2 导出的 dma-buf fd 通过 mpp_buffer_import 导入，再用 mpp_frame_set_buffer 绑定。需匹配 NV12 布局与 stride，并保证编码使用结束后才归还采集缓冲；当前代码包尚未实现此链路。
08 / 音频与网络

音频同步录制与实时推流

视频走硬件编码，音频走 ALSA + 软编 AAC（数据量小，CPU 占用可忽略），在 mux 元件按时间戳同步。

音视频同步录 MP4

gst-launch-1.0 -e \
  v4l2src device=/dev/video44 num-buffers=600 \
  ! video/x-raw,format=NV12,width=1920,height=1080,framerate=30/1 \
  ! mpph264enc ! h264parse ! queue ! mp4mux name=mux faststart=true \
  ! filesink location=av.mp4 \
  alsasrc device=hw:0,0 \
  ! audio/x-raw,rate=44100,channels=2 \
  ! audioconvert ! voaacenc ! aacparse ! queue ! mux.

AAC 编码器二选一：voaacenc（GStreamer Bad Plug-ins）或 avenc_aac。05 脚本会探测声卡和编码器，缺少时退化为纯视频。纯音频测试：arecord -D plughw:0,0 -f cd -d 5 a.wav。

录制结束方式：05 脚本只限制视频帧数，音频源会持续采集，因此有音频时可能不会在 20 秒后自动退出。使用 Ctrl+C 让 gst-launch-1.0 -e 发送 EOS 并完成 MP4 封装；精确定时停止需后续统一控制两路源。参考 GStreamer 命令说明。

09 / 性能与优化

让 4K 实时、低延迟、低 CPU 的关键设置

按收益从高到低排列。所有吞吐结论以板子自测脚本的实测 fps/码率为准。

必做项

  • CPU 性能模式：echo performance | tee /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor
  • 全程 NV12：RKISP 直接输出 NV12，编码器也收 NV12，避免任何 CPU 色彩转换
  • 缩放交给 RGA：4K 转 1080p 用硬件 videoscale/RGA，不要软件 videoconvert
  • stride 对齐：水平 16、垂直 16 对齐，直接采用 V4L2 返回的 bytesperline
  • CBR + 合理码率：1080p≈4Mbps、4K≈12Mbps 起步，按画质实测调整

进阶项（多路 / 4K / 产品化）

  • dma-buf 零拷贝：V4L2 与 MPP 共享 fd，省每帧 memcpy（4K 单帧 11.9MB）
  • queue 防阻塞：tee 支路加 queue leaky=downstream，显示慢不拖编码
  • 低延迟：缩短 GOP、关闭 B 帧、编码器 zerolatency、udp sync=false
  • 多路：每路独立 v4l2src+mpph264enc 实例，VENC 支持多实例，实测路数受总吞吐约束
  • 动态码率/ROI：用 MPP MPP_ENC_SET_RC_CFG、ROI 接口按场景调画质
已知坑（官方 FAQ）：① 4K@30 流畅、4K@60 可能卡顿，必要时降帧或上 AFBC；② 该固件版本部分平台 RGA 可能异常，若 RGA 报错先用 videoconvert 兜底并以实测为准；③ 播放卡顿先查是否硬解（echo 0x100 > /sys/module/rk_vcodec/parameters/mpp_debug 看日志）。

11 / 故障排查

常见问题

打不开 /dev/video44 / No sensor attached

IMX415 已连接时仍出现 “No sensor attached”，应检查 sensor 驱动识别、所接接口与固件配置，以及 rkaiq / ISP 链路。先按 IMX415 验证步骤 确认实际采集节点；若需重新插拔排线，先断电。不要仅凭 video44 节点存在判断连接正常。

没有 mpph265enc 插件

当前板子上已通过 gst-inspect-1.0 mpph265enc 检出 Rockchip 插件。换固件后若缺失，先跑 00 自检，检查 GStreamer Rockchip 插件包或 SDK 中的实现。

编译报找不到 rk_mpi.h

当前板子已有 librockchip-mpp-dev，头文件位于 /usr/include/rockchip。换板或固件时先核对头文件与运行库版本，再安装该开发包；当前路线二 Makefile 不使用 RGA。

无显示器怎么编码

03 脚本检测到无 DISPLAY/Wayland 会自动用 fakesink，只录文件不弹窗，可全程 ssh/adb shell 运行。

电脑 VLC 拉不到 UDP 流

确认 host 填电脑 IP（192.168.2.165）、与板子同网段；Windows 防火墙放行 VLC/UDP 5000；VLC 打开 udp://@:5000 后再启动推流。

4K 卡顿 / 掉帧

开 performance 调速；确认走的是硬编（top 中 CPU 应很低）；缩到 1080p 用 RGA；4K60 官方不保证，按 30fps 设计；必要时上 dma-buf 零拷贝。
